# 《菲菲更名宝贝》实证分析与跨平台重构方案

> 阶段 1（原版实证）+ 阶段 2（重构方案）合并交付。  
> 本文所有"已确认"结论来自对用户提供的 `FFRenamePro.exe` 的静态实证（PE/资源/窗体流解析），不是网络截图推测；未实际启动程序，涉及"操作行为"的结论单独标注为「推断」。

---

## 0. 结论摘要

1. **原版是 64 位 Delphi / VCL 程序，UPX 加壳，未签名**。内嵌 **80 个 Delphi 窗体/框架（DFM）**，可完整还原菜单、工具栏、页签、控件层级与默认值，功能分区清晰但高度密集。
2. **原版界面骨架**：菜单（7 个顶级菜单、135 项）→ 图标工具栏（31 个按钮）→ 路径/过滤工具条 → 主工作区（左：命令列表/小提示，右上：9 类文件列表页签，右下：8 个顶层功能页签）→ 状态栏 + 进度面板。
3. **核心体验必须保留**：文件列表 + 实时"原名 → 新名"预览、左侧命令列表（可编辑的操作记录）、六组基础更名规则、扩展名规则、预览/应用/撤销、过滤与遍历、方案与快照、冲突处理。
4. **主要痛点**：1058×642 固定像素布局、控件挤在大页签里、Win32/第三方老控件渲染、无 DPI 感知（高分屏位图缩放发虚）、无长路径感知、无搜索/无快捷筛选、撤销反馈弱、设置项藏在多层对话框里。
5. **新方案**：Tauri 2 + React 19 + TypeScript + Vite，Rust 负责文件系统与事务化改名/撤销；界面改为「左侧功能导航 + 中部文件列表 + 右侧可折叠规则链 + 底部执行条」；保留命令列表语义（改造成规则链 + 操作记录抽屉），9 类列表收敛为可切换的列表类型。
6. **本阶段只交付方案与静态设计稿**，未编写原型工程（按你的最新要求停在设计确认前）。

## 1. 阶段 1：原版实证

### 1.1 样本与分析方法

| 项目 | 内容 |
| --- | --- |
| 样本路径 | `<用户目录>\.trae-cn\attachments\...\FFRenamePro.exe`（用户提供，原始路径含本机用户目录，发布版已脱敏） |
| 文件大小 | 12,325,888 字节（外壳）；UPX 解包后 37,904,384 字节 |
| SHA-256 | `feaa0ea6caad90e1dda09cd708fb992497feb2ebb8231960d5ca2f674d5aadd6` |
| 分析方法 | 1) `Get-Item`/`Get-AuthenticodeSignature` 读取版本与签名；2) `pefile` 解析 PE、导入表、资源目录、Manifest；3) 用 `upx -d` 解包副本；4) 解压/解析 RT_RCDATA 中的 **TPF0 二进制 DFM**，还原 80 个窗体/框架的对象树与全部字符串属性；5) 对照官方帮助页与教程校验功能命名。 |
| 分析边界 | 未复制、未再分发原版图标/位图/代码；只提取结构与文本用于功能还原，新界面全部自绘。 |

> 说明：静态解析能确认"界面上有什么、控件叫什么、默认值是什么"，但不能确认每个功能运行时算法细节（如"智能更名"的完整决策顺序）。此类结论在表中标为「推断」。

#### 1.4.6 原版的"命令列表"模型

- 列：序号、命令 ID、功能、代码、状态（5 列）。
- 可"结束当前命令（插入空命令）"、保存/载入批处理（文本文件）、最近文件列表、删除最后一条、清空。
- 每完成一次规则设置（点 `Ok`）写入一条命令；应用/撤销后可配置"自动清除所有命令"。

> 这等价于 **可编辑的操作流水账**，是原版最有价值的交互资产之一：用户能看到自己"做了什么"，并能保存复用。新方案以「规则链」承载，同时保留"操作记录"作为只读时间线，两者共享同一份命令模型。

### 1.6 必须保留的核心体验 vs 可改进的老设计

**必须保留**

1. 文件列表里直接看到**原名 → 新名**的对照与状态，不是"填个规则点执行"的黑盒。

## 2. 阶段 2：重构方案

### 2.1 技术选型（已实测本机工具链）

| 项 | 实测结果 |
| --- | --- |
| Node.js | v26.13.0 |
| npm | 11.20.0 |
| pnpm | **未安装**（改用 npm） |
| Rust | rustc 1.99.1 / cargo 1.99.1 |
| MSVC | Visual Studio 18 Community（含 VC Tools） |
| WebView2 | 156.0.4314.58 |
| Python | 3.14.10（仅用于本次静态分析） |

**推荐：Tauri 2 + React 19 + TypeScript + Vite**

理由：
1. 安装包/内存远小于 Electron（典型 10–20 MB vs 80–150 MB），对一个"文件工具"更符合直觉。
2. 文件枚举、批量改名、属性/时间修改放在 Rust 侧，路径与 Unicode 处理可控，适合做**事务化改名与崩溃恢复**。
3. 原生对话框、拖拽路径、系统托盘/右键菜单集成成熟；Windows 依赖 WebView2（Win10+ 自带）。
4. 前端只负责规则编辑与预览，Rust 作为唯一执行者，天然形成"预览/执行"边界。

**Electron 备选（触发条件）**：团队没有 Rust 维护能力、或需要直接复用 Node 生态（如现成的 Node 元数据解析库、脚本引擎），或 Tauri 在目标 Linux 发行版 WebKitGTK 兼容性无法满足。取舍：

| 维度 | Tauri 2 | Electron |
| --- | --- | --- |
| 体积/内存 | 小 | 大 |
| 文件系统性能 | 原生 Rust，高 | Node fs，足够 |
| 跨平台一致性 | WebView 引擎不同（WebView2/WKWebView/WebKitGTK） | 统一 Chromium |
| 打包成熟度 | 好（msi/dmg/AppImage/deb） | 很好 |
| 崩溃恢复/事务 | Rust 实现更稳 | 需自行设计 |
| 脚本扩展 | 需引入 JS 引擎 | 天然 Node |

### 2.2 架构设计

```
┌───────────────────────────── React 19 + TS ─────────────────────────────┐
│ 视图层：文件列表 / 规则链 / 预览差异 / 历史 / 设置                        │
│ 规则引擎（纯 TS 函数）：Rule[] + FileEntry → RenamePlan（即时预览）        │
│ 状态：Zustand（选择、规则、预演结果、主题）                               │
└───────────────────────────────┬──────────────────────────────────────────┘
                    Tauri invoke（JSON Schema 校验）
┌───────────────────────────────┴──────────────────────────────────────────┐
│ Rust 核心（src-tauri + ffrn-core）                                        │
│ 1. scan_paths：遍历/过滤/符号链接环检测/元数据读取                        │
│ 2. validate_plan：跨平台合法性、保留名、长度、大小写/Unicode 归一化冲突    │
│ 3. apply_plan：两阶段临时名改名（支持交换/仅大小写变更），逐项日志         │
│ 4. undo：按批次反向恢复（含时间/属性还原），启动时自动检测未完成事务       │
│ 5. 元数据（P1）：EXIF/IPTC、ID3、Office、PDF、文本编码                    │
└──────────────────────────────────────────────────────────────────────────┘
```

**为什么规则引擎放前端**：预览必须"输入即算"，10 万行也要 60fps；规则求值是纯函数，易于单测。**Rust 不信任前端**：执行前重新校验每个目标名，并在系统层面处理大小写/归一化/已存在文件，避免竞态。

**规则数据模型（草案）**

```ts
type Rule =
  | { type: 'add'; text: string; anchor: Anchor; mode: 'direct' | 'pad'; padTo?: number; padChar?: string }
  | { type: 'replace'; find: string; replace: string; caseSensitive: boolean; nth?: number; regex?: boolean }
  | { type: 'delete'; mode: 'range' | 'between' | 'charset'; ... }
  | { type: 'number'; expression: string; start: number; step: number; digits: number; groupBy?: 'path' }
  | { type: 'move'; ... }
  | { type: 'case'; mode: 'upper' | 'lower' | ...; wordSep?: string; exceptions?: string[] }
  | { type: 'ext'; mode: 'add' | 'replace' | 'remove' | 'number' | 'case' | 'fixed' | 'smart'; ... }
  | { type: 'time'; target: 'created' | 'modified' | 'accessed'; strategy: 'fixed' | 'self' | 'exif' | 'expression'; ... };
```

命令列表仍然存在：`Command[]` 是规则链的可序列化形态，保存/载入批处理即导入导出该数组。

### 2.4 关键交互设计

1. **规则链**：卡片式纵向堆叠，顺序即执行顺序；拖拽排序；每张卡有启用开关、摘要、展开编辑、删除。保留"逐条 Ok 生效"的等价体验：编辑卡片时**即时预览**，点"应用此规则"才加入链。
2. **即时预览**：任何输入 150ms 内更新新名列；大列表用虚拟滚动与增量计算；"自动预览"可关。
3. **冲突可视化**：行内红色状态 + 原因（目标已存在 / 同批次重复 / 非法字符 / 超长 / 保留名）；顶部汇总 chip；提供"自动编号/跳过/替换"三种一键处理。
4. **执行与撤销**：应用前弹"预演清单"（可展开每个文件），执行中逐项进度与失败原因；完成显示"成功 117 / 跳过 1 / 失败 0"，提供"撤销本次"。
5. **拖拽**：拖入文件/文件夹即添加；悬停高亮投放区；拖入文件夹时可选择递归。
6. **键盘**：`Ctrl+O` 添加、`Ctrl+Z` 撤销、`Ctrl+Enter` 应用、`Space` 勾选、`Delete` 移除、`F2` 行内编辑新名、`/` 聚焦搜索。
7. **可访问性**：焦点环、ARIA 标签、对比度 ≥ 4.5:1、支持仅键盘完成核心流程。
8. **布局记忆**：面板宽度、列表列宽、主题、最近路径持久化。

### 2.5 跨平台差异与兼容性处理

| 问题 | Windows | macOS | Linux | 方案 |
| --- | --- | --- | --- | --- |
| 路径分隔符/盘符 | `\`、`C:\` | `/`、`/Volumes` | `/` | Rust `PathBuf`；展示用系统分隔符；禁止手拼字符串 |
| 大小写敏感性 | 默认不敏感 | 默认不敏感（APFS 可配置） | 敏感 | 冲突检测按文件系统探测（创建临时探测文件或用 `stat` 比较大小写变体）；仅大小写改名走临时名两阶段 |
| 非法字符 | `< > : " / \ | ? *`、控制字符、结尾点/空格 | `/`、NUL（Finder 显示 `:` 为 `/`） | `/`、NUL | 默认采用"跨平台安全集"（Windows 规则），可在设置中切换"仅本平台" |
| 系统保留名 | CON/PRN/AUX/NUL/COM1-9/LPT1-9（含带扩展名） | 无 | 无 | 统一按 Windows 保留名拦截（可关闭），避免方案跨平台失效 |
| 长路径 | 组件 255、整路径 260（除非 longPathAware + 注册表） | 组件 255（UTF-16 计数） | 组件 255 字节、路径 4096 | Tauri 打包启用 `longPathAware`；Rust 使用 `\\?\` 前缀；UI 显示字符数/字节数预警 |
| Unicode 归一化 | 基本 NFC | APFS 常为 NFD 变体 | 原样 | 冲突比较前统一 NFC/NFD 归一化 + 不区分大小写比较（按平台） |
| 文件名编码 | UTF-16 底层，Rust `OsStr` 无损 | UTF-8 | UTF-8 | 全链路 UTF-8；禁止用 ANSI API；不做隐式转码 |
| 只读/属性 | 文件属性 A/R/H/S、ACL | `chflags`（隐藏/uchg）、POSIX 权限 | POSIX 权限、扩展属性 | 属性面板按平台能力显示；不可用项置灰并解释；只读映射到写权限 |

| 符号链接 | 支持 | 支持 | 支持 | 默认不跟随目录符号链接，检测环；改名作用于链接本身 |
| 右键菜单集成 | 注册表 | Finder 服务/快捷指令 | Nautilus 脚本/`.desktop` | 按平台实现，默认不安装，设置中显式开启 |
| 打包/签名 | MSI/NSIS，未签名会 SmartScreen | dmg，需签名+公证 | AppImage/deb，可选 Flatpak | CI 分平台构建；文档说明签名要求 |
| 内码/代码页转换 | 依赖 Windows 代码页 | 有限 | 有限 | 标记为 Windows 专属能力，跨平台隐藏或降级为 UTF-8/GBK 常见转换 |
| 文件加密（EFS） | 支持 | 不支持 | 不支持 | 明确标注平台限制，不做伪实现 |
| Pascal/Python 脚本 | 原版内置脚本引擎 | 同 | 同 | **不内嵌 Python/Pascal**；P2 提供受限 JS（QuickJS/WASM）脚本，默认关闭并沙箱化 |

**"在新系统上的小问题"对应缺陷**（可直接用于验收清单）：

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 高分屏字体发虚/控件错位 | Manifest 无 DPI 感知 + 固定像素布局 | 矢量 UI、`rem/px` 自适应、系统缩放 125%/150%/200% 三档实测 |
| 拖到受保护目录失败 | asInvoker + 无错误解释 | 明确提示权限/路径，不自动提权 |
| 中文路径乱码 | 旧 ANSI API 混用 | 全 Unicode 路径，Rust `OsStr` |
| 超长文件名被截断/失败 | 无 longPathAware、260 限制 | 长路径支持 + 预检 + 可配置策略 |
| Windows 上仅改大小写失败 | 大小写不敏感 + 目标被视为已存在 | 临时名两阶段改名 |
| macOS 上重名判断失灵 | NFD 归一化差异 | 归一化比较 |
| Linux 上脚本/编码功能异常 | 依赖 Windows API/代码页 | 功能分级 + 平台能力探测 |
| 旧配置升级后报错（原版官方也提示重置） | INI/注册表结构变更 | 版本化配置 schema + 迁移器 + 损坏自动备份重置 |

### 2.6 分期实施计划

> 目标：先做"可用且可信"的批量改名，再做"元数据全家桶"。避免一次性追求功能对齐。

### 2.7 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 原版规则语义复杂（位置/边界/间隔符） | 预览与用户预期不一致 | 为每组规则建立"行为样例集"，以原版操作结果为准做回归（用户可提供对照截图/结果）；先做高频子集 |
| 命令列表 DSL 未文档化 | 批处理兼容性 | 定义新 JSON 方案格式；提供"从文本命令导入"的兼容层（P1），并明确不完全兼容项 |
| 事务化改名在崩溃时留下临时名 | 文件"丢失"感 | 先写 journal 并 fsync，再改名；启动扫描未完成事务并提供一键恢复；临时名带可识别前缀 |
| 目标文件已存在/竞态 | 覆盖风险 | 默认**绝不覆盖**；执行前二次 stat；冲突即中止该批次并回滚 |
| 大小写/归一化误判 | 误报冲突或漏报 | 平台探测 + 归一化比较 + 单元测试矩阵（Win/macOS/Linux） |
| 第三方元数据解析不完整 | 元数据功能缩水 | 先只读高置信字段；写入功能按格式逐个开关 |
| Tauri WebView 差异 | macOS/Linux 样式/性能差异 | 设计稿在三大引擎的关键页面回归；避免依赖 Chromium 私有特性 |
| 未签名/未公证 | 安装被拦截 | 文档说明；后续接入签名（Windows EV/OV、Apple Developer ID） |
| 与原作者的知识产权边界 | 法律风险 | 只复刻功能行为与信息架构，界面/图标/文案全部自绘重写；不使用原版名称作为产品名（工作名「更名工坊」），发布前做名称与合规评估 |
